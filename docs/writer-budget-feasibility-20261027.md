# 完整流程预算：固定约束冲突审查

2026-10-27。继续步骤 215 时，先核对完整预留是否有可能在当前计量下满足 100 万上限。本次没有改动模型、预算策略、来源、修复次数或科学交付门禁，没有新模型请求。

## 结论

**目前的 100 万硬上限、完整两次修复保障、既有保守计量和固定输出上限不能同时满足。** 这与之前约 478 万的上下文宽上界不同：本次仅计算完整最大路径中已知的必要部分，即使忽略全部未来正文和 Evaluation 输入，也已超限。

| 固定题目 | 必要部分预留 | 加 10% 并向上取整后的下界 | 100 万内可准入 |
|---|---:|---:|---|
| few-shot | 934,874 | 1,030,000 | 否 |
| ViT | 978,197 | 1,080,000 | 否 |
| NeRF | 979,653 | 1,080,000 | 否 |

**这些数字不是实际账单，也不是模型实际完成任务至少消耗的 tokens。** 它们是按现有 UTF-8 保守计量及规定的最大输出，兑现完整预留承诺所需额度的必要部分。实际费用只能由真实 usage 确定。

## 可复算的证明

允许的最大合法路径是：五章正文、首次摘要、一次 Reviewer、首次完整 Evaluation；随后两次正文修复，各自可能需要摘要更新和完整复评。完整 Evaluation 包括一次抽取、最多八批支持核验、一次全局检查。

| 阶段 | 请求数 | 每次最大输出预留 |
|---|---:|---:|
| 正文 | 5 | 20,000 |
| 摘要及两次更新 | 3 | 20,000 |
| Reviewer | 1 | 4,096 |
| 正文修复 | 2 | 20,000 |
| 断言抽取 | 3 | 16,384 |
| 支持核验 | 24 | 16,384 |
| 全局检查 | 3 | 16,384 |
| 合计 | **41** | **695,616** |

阶段数及输出预留从现有 `complete_writer_plan` 读取。两次修复成功与否未知，不能提前假设首稿通过或第一候选成功；三个版本的断言数也不能以旧稿数量代替 128 上界。

现有 `strict_request_reservation` 还对每次请求增加 1,024 包装预留，41 次合计 41,984。该数从实际计量函数测得，不另建规则。

真实正文请求构造器与 `WriterSession.patch` 均携带整个冻结 `packet`，因此五章和两次正文修复至少携带七份 packet 成员字节。摘要及其更新只读取正文依赖，**未计入七份来源拷贝**。实际消费者测试只替换外部传输，确认五章和两个修订请求保留完整 packet。

三域单份 packet 成员分别为 28,182／34,371／34,579 字节；不计最外层花括号，更不计嵌入消息时的二次转义。

```text
必要部分 R_floor = 695616 + 41 × 1024 + 7 × packet_member_bytes
计算额度下界 = max(500000, ceil(1.1 × R_floor / 10000) × 10000)
```

已忽略的非负输入包括所有系统提示、native schema、前章及修订正文、摘要与 Reviewer 输入、诊断、全部 Evaluation 输入及完整原始支持文本、额外请求字段和转义。它们只会增加完整预留。因此，继续收紧这些未知输入的上界，不能消除已经存在的必要部分超限。

这也不意味着将上限改成 108 万就能完成：完整上界尚有大量输入未计入。**下界只能用于排除；低于上限也不能据此准入或付费。**

## 下一项设计取舍

已提出两种选择，收到选择前保持当前规则：

1. 保留 100 万硬上限。始终保障首次完整 Evaluation；在写作前，用完整路径上界确定并锁定本轮可用修复次数（0–2 次）。不能运行到一半才宣布没有修复额度，也不能以支持率不足的草稿交付。此方案需要明确调整“每轮都预留两次完整修复”的要求，仍须重新证明三域完整准入。
2. 保留两次完整修复保障。重新设计并验证计量与预算方案，原始材料和输出预留不裁剪；完整准入前继续不付费。本审查不据下界替用户盲目选择更高额度，也不把新 token 计量当作已经验证。

这是一项设计取舍，不是重新索取已有付费权限。两种方案都不改变科学支持率 1.0、完整核验、核心覆盖和全局一致性要求。
