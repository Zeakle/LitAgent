# ADR-001: Retain Qdrant and Select the Paper Embedding by Benchmark

- Status: Accepted
- Date: 2026-07-18

## Context

The running system already uses Qdrant collections for dense and sparse retrieval,
with Qdrant-side reciprocal-rank fusion (RRF). Earlier planning documents still
described a future `pgvector + HNSW + SPECTER2` implementation and a two-million
paper corpus. Those statements are not supported by the current runtime or
corpus evidence, and they incorrectly couple two independent decisions:

1. the vector-store implementation; and
2. the embedding model used to create vectors.

## Decision

1. Qdrant remains the authoritative vector store for paper and claim retrieval.
   Phase 14 will not introduce a migration to pgvector.
2. The current embedding model remains the reproducible baseline. SPECTER2 is a
   candidate, not a default architecture requirement.
3. Phase 14.5 will compare the baseline and candidates on a versioned benchmark
   set using retrieval quality, latency, index footprint, and survey-level
   faithfulness. A candidate is adopted only when the recorded result justifies
   its operational cost.
4. An embedding experiment creates a new versioned Qdrant collection. Vectors
   generated by different models must not share a collection or be compared as
   if they were interchangeable.
5. Paper and query encoders, corpus manifest, chunking policy, collection name,
   and benchmark version are part of the retrieval artifact and must be recorded
   with each benchmark result.

## Consequences

- The project keeps Qdrant native dense/sparse search and server-side RRF,
  avoiding a speculative data-store migration.
- SPECTER2 can demonstrate domain-aware retrieval only through measured evidence;
  it is not added merely as an interview keyword.
- Corpus ingestion, stable paper identifiers, content hashes, collection
  versioning, and benchmark fixtures become Phase 14 prerequisites for a
  credible retrieval claim.

## Alternatives Considered

### Migrate to pgvector and hard-code SPECTER2

Rejected. It creates a costly migration before a retrieval baseline exists and
makes the store choice appear dependent on an embedding model.

### Keep the current model permanently without evaluation

Rejected. The existing baseline is useful for reproducibility but does not prove
that it is the best model for scholarly-paper retrieval.
