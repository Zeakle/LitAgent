# 分阶段扩容、Jev 与正文质量闭环

本页说明源码中的新服务端扩容配置。已发布 v0.1.0 与当前 8000 只读演示仍保存055原始结果；扩容不会重算历史评分，也不代表真实科学验收通过。

## 新配置

使用 `config/expanded-capacity.yaml`，保留 `config/default.yaml` 的历史默认。冻结写作入口接受 `--config`，准备与执行必须使用相同配置指纹；只适用于新建 `planned-budget-v7` 任务。普通 API 不新增任意额度或端点参数。

| 阶段 | 原输出上限 | 扩容配置 | 语义 |
|---|---:|---:|---|
| 查询规划 | 8,192 | 16,384 | 子查询仍最多三个，不增加检索任务 |
| Extractor | 配置2,048；严格路径已为8,192 | 8,192 | 不把已有严格8K描述为新增四倍；仍需原文定位与语义核验 |
| 正文、摘要、正文修复 | 20,000 | 24,576 | 关闭思考，正文容量与核心问题不增加 |
| Reviewer | 4,096 | 16,384 | 对应055的直接输出瓶颈 |
| Evaluation抽取／支持核验／全局 | 16,384 | 32,768 | 完整保留所有断言和实际引用；清单恢复使用同一核验输出额度 |

正文／修复请求超时600秒，摘要／Reviewer／Evaluation为300秒；Evaluation总时限7200秒，写作审阅任务3600秒，DAG7200秒。扩大等待与输出不能承诺服务一定完成，超时或输出截断仍保存原响应、usage并明确失败。

新配置的处理上下文为196,608 tokens，继续保留10%余量；并分别锁定修复、抽取和全局检查的完整请求额度。上下文扩大不代表每次请求都填满，实际计量与总预算照常生效。

这些是最大输出预留，不是目标篇幅、实际费用或质量分数。每题450万tokens／64请求、两次共享修改、零传输重试、上下文至少10%余量保持。正文66单元、每单元2000字符及摘要结论各2单元不因输出扩容而增加；断言由既有动态扩批在完整剩余预算内处理。Jev独立服务的原额度保持，不自动启用。

```sh

.venv/bin/litagent config --config config/expanded-capacity.yaml --validate-only
```

三份既有冻结材料的完整预算分别为447万／450万／449万tokens，各62请求；它们不重新搜索或提取。普通Survey仍须计入已发生的准备费用和请求，不能把冻结材料准入冒充任意主题准入，更不能把历史提取费用显示为零。

配置选定后，七阶段输出额度进入冻结envelope及预算身份。实际生成、Reviewer、Evaluation、扩批、清单恢复、费用重放均核对同一额度。省略该字段保留历史值与旧计划身份；不能以新额度恢复055。未来额度不能被前置调用挪用，未知usage占用不释放、不自动重发。

完整预算准入与单请求容量检查仍会拒绝超范围材料。保证应表述为：已知容量问题在发送前检查，遵守冻结规模的后续步骤有对应预留；不能表述为“任意正文永不超限”。模型违反输出契约、证据不足、来源错误或服务异常仍可能失败。

## Jev 当前位置

当前 `strict_auto_v2` 在启用 `verification.jev` 时使用以下路径：

`Extractor → 候选账本 → 章节选材 → Jev提取核验 → 冻结通过材料 → Synthesis → Reviewer → Evaluation／有限修复`。

Jev检查候选claim、非空语义字段及其关联是否被同一条完整原文支持；检查对象不只是压缩后的claim。使用固定 `jev-1.13.0` 与TypeSafe官方接口。整组要求 `supported`，对应证据要求 `contributes`，各项confidence至少0.9；技术完整性、模型身份和usage也必须通过。低置信度／不支持项保留诊断但不作为通过材料；过滤后缺核心材料仍阻止交付。关闭时明确 `disabled`，不假装通过；055明确关闭。

手动报告版本核验仍可选终稿Jev，它与前置过滤用途不同，不替代运行内Evaluation。前置通过仅说明提取内容获给定原文支持，不保证论文客观正确，也不证明生成后的比较、概括和引用归属正确。官方模型文档：<https://docs.typesafe.ai/models>；接口：<https://docs.typesafe.ai/api/system-one>。保留项目固定版本与原200k输入／20请求、16问题／批、并发2、24kbytes请求体、30秒、零重试，不启用实验长上下文。

## 如何闭环质量，是否需要HITL

现有流程已经包含Reviewer、完整Evaluation、最多两次共享恢复／正文修复及完整复评。先使已有环节可达，不增加新Agent或无限重试。清单恢复最多一次；若它占一次，正文修复只剩一次。失败候选不得覆盖正式正文，修复后必须重新检查摘要、结论、全部科学断言、核心覆盖及全局一致性。

容量问题由程序解决；科学问题按定位诊断修复；核心证据不足需要明确缺口。冻结后新增材料必须创建新证据版本，不能为通过Evaluation临时换引用或用其他论文兜底。

本轮保留无人审批默认。HITL建议作为材料不足、两个修改机会耗尽或判断冲突后的可选人工编辑／校准入口；不是Reviewer容量的解决办法。人工改稿必须新建版本与SHA并重新完整核验，不能人工覆盖自动门禁失败。若需对真实科学可靠性作强结论，仍需独立人工校准和保留集；自动支持率1.0仅是当前评估契约下的通过条件。
