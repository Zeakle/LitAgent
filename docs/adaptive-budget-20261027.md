# 100 万硬上限：写作前锁定可承担的修复次数

2026-10-27，用户选择保留 100 万上限。新增显式 `planned-budget-v3`，原 `planned-budget-v2` 的两次完整修复预留及历史身份不变；旧 API 默认仍为 `legacy`。

## 当前实现

- 每题最高 1,000,000 tokens／64 请求，按原保守计量和 10% 余量规划，运行中不扩额。
- 在写作前依次比较 2、1、0 次共享修复的完整合法路径，选最大的可准入次数并锁定。每次修复都计入必要摘要更新和完整复评；不是只预算一次 rewrite 请求。
- 所有候选始终包含五章、摘要、Reviewer，以及首次完整 Evaluation：128 条模型断言容量、最多八批支持核验、独立抽取与全局检查。任何必需阶段缺失都拒绝。
- 无修复的完整路径为 17 请求，一次修复为 29 请求，两次为 41 请求；已发生的准备用量和请求仍计入本轮。
- WriterSession、本地原生修复、范围修复及 runner 的 Evaluation 修复读取同一锁定次数。0 次不发修复请求，也不把科学失败改成通过。
- Pro 关闭思考；Reviewer 和 Evaluation 继续使用 Lite。20,000／4,096／16,384 输出预留、严格科学支持率 1.0、核心覆盖和完整性检查保持。
- RunOptions、API、服务端 profile、冻结身份、账本恢复、质量页及同源导出均识别 v3。新 profile 为 `writer_disabled_responses_planned_budget_v3`。
- 被拒绝计划标记 `repair_allocation=unallocated`；只有准入后才为 `locked`。首次 Evaluation 的“已计入”与“已预留”分别记录。预留和未分配候选都不是实际费用。

真实消费者测试还发现旧修复预检在 `Session.call` 前缺少 request scope。已将预检与实际发送绑定到同一个 `repair_N`；SDK 测试只替换 HTTP，确认一次额度只发送一次请求，额外修复在发送前拒绝。
