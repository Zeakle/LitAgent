# 已批准设计：只对EOF容器缺闭合做确定性语法归一化

**用户于2026-10-26明确回复“批准语法修复草案”。** 以下保留原设计及确认原因；首版仅通过服务端固定验收profile接入，普通API和旧策略不变。实施与验收记录见[政策实现审查](writer-eof-policy-review-20261026.md)。不恢复016、不回算历史报告或评分；真实验证仍须先完成离线验收并冻结独立的一次性清单。

## 为什么需要单独确认

此前已确认的计划明确要求：“无法解析的JSON……不能通过补括号或删除字段接受”，并把首次生成后的修改统一计入两次共享额度。本草案拟调整这两项语法与计次边界，不能把它包装成不改变契约的小修复。[项目规则](../AGENTS.md)也要求架构与数据流变更先确认。已有付费调用授权仍有效，这里不重新申请付费权限。

016分类、方法、综合比较三份响应中已出现的科学文本与引用单元均完整，但最外层缺少闭合容器。私有诊断仅追加推导出的EOF闭合符，不改任何原始字节，三份候选均通过完整宿主schema，全部单元语义、引用和顺序一致；前两份候选的SHA甚至与真实额外模型恢复响应完全相同。12个未闭字符串、池外引用、中部漏逗号及错配容器反例均拒绝。**这只是3个实际样本与12个反例上的语法可行性，不是科学正确性或正文完整性证明**；没有保存为可交付报告，没有新增模型调用，也不证明模型原计划没有更多内容。

## 拟议边界

保留grounded-writer-v1的科学字段、原有Worker、五类正文、宿主引用、完整原文及唯一报告出口。新增版本化语法政策；旧政策继续要求完整合法JSON，新政策仅在明确冻结的运行中允许下述归一化：

1. 原始HTTP文本、来源、schema和请求身份先完整保存，不覆盖原响应。
2. 仅接受从首字符开始合法、字符串和转义均已闭合的JSON前缀。中间语法错误、截断字符串、重复键、未知字段、孤立段落、引用越权、缺少必需字段等一律拒绝。
3. 唯一可追加内容是解析栈推导出的末尾`]`或`}`。不得补逗号、冒号、引号、值、单元、引用或科学正文，不得调整顺序。每份响应最多归一化一次，继承既有字节、深度、对象数量及运行请求上限。
4. 归一化候选必须通过完整宿主schema、完整原字符串覆盖、容器归属及前后语义指纹一致检查，再进入正常编译。保存raw SHA、追加符、候选SHA、宿主/供应商schema SHA、单元原始位置及政策版本。
5. **只有纯语法归一化作为初始编译的一部分，不消耗两次模型/语义修订额度。** 这正是本草案拟改变的计次语义；任何正文词句、条件、数值或引用修改仍共用最多两次，不新增修改池或模型重试。
6. 没有资格归一化的响应按原协议失败收敛；不新增第三次模型修复。结果未知、缺usage、身份不符等财务和恢复边界不变。

首版仅允许正文、摘要/结论的首次生成响应使用该政策；Reviewer、Evaluation及独立核验的判断响应仍要求原始JSON完整合法，不适用归一化。不能在真实运行中临时扩大适用阶段。

## 质量要求不变

归一化不能证明模型原本不打算继续输出，也不能证明核心问题已回答。完整正文、摘要/结论、Reviewer、独立断言抽取、逐批Evaluation、科学支持率1.0、核心覆盖、引用归属及全局一致性仍必须全部通过。正文不完整、证据不足、重复填充或科学事实错误仍不可交付。Judge/Jev独立可选，既定三域验收仍关闭，无人工审批节点。

本草案不增加预算、超时、模型、检索或来源：仍每题500000 tokens/64请求、两次语义修改、零传输重试；归一化不调用LLM。原始响应可以保持“语法不完整”，新候选单独记录归一化事实，不能冒充供应商原始合法输出。
